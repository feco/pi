---
name: implement
description: "Use before editing code to implement any requested feature, bug fix, refactor, ticket, spec, plan, or behavior change."
---

Implement the work described by the user in the spec or tickets. Before changing code, discover the project's applicable implementation, testing, verification, documentation, and versioning instructions — they are authoritative throughout.

Work through these steps in order. Do not start a step until the previous step's completion criterion is met; "the tests will be added later" means the work is unproven, not mostly done.

Use the role-specific agents when delegating: `test-writer` for tests, `implementer` for production code, `code-reviewer` for correctness, `test-reviewer` for test quality, `thermonuclear-reviewer` for structural quality, and `global-reviewer` for end-to-end impacts. Reserve `delegate` for work outside these roles. For tiny changes you may edit files directly to save time and cost; this writer exception does not skip the automatic review step.

1. **Mini-grill (chat only).** Before any implementation, including tiny direct edits, inspect the relevant repository context and ask 1–3 decision-focused questions with recommended answers. Find repository facts yourself. Reuse decisions already settled by the user, including an earlier `grill-with-doc`; ask only about remaining decisions, or ask the user to confirm your proposed scope when none remain. Wait for answers; follow up only on blockers. Keep this session in chat: create no grilling, spec, or plan document. The user initiates `grill-with-doc` for larger work; do not start it automatically. Done when the user has settled the questions and no blocking decision remains.
2. **Visual plan and approval.** Show a concise implementation plan with an ASCII visual of the affected flow or change, the intended red/green slices, and verification. Wait for explicit approval before editing tests or production code or dispatching a writer. This gate runs once before the loop; return to it only if scope or a material decision changes. Done when the user approves the plan.
3. **Red/green slices.** Follow the `tdd` skill and complete each vertical slice before starting the next:
   1. Dispatch `test-writer` to write exactly one behavior-focused test at a confirmed seam. Run the narrowest relevant RED command in the child if allowed; otherwise the orchestrator runs it after test handoff. Done when the observed result fails for the intended reason. Do not force tests when not relevant.
   2. Dispatch `implementer` to make that test pass with the minimum production-code change. Run the focused GREEN command in the child if allowed; otherwise the orchestrator runs it after implementation handoff. Done when the observed result passes and the change meets the full rules of the thermo-nuclear-code-quality-review skill. Follow `~/.pi/agent/GUARDRAILS.md` for headless evidence attribution. Implementer should report implementation that might need an ADR to add it later in the documentation, only if the change is significant enough and that decision is likely to need explanation later.
   3. Repeat for the next behavior only after the current slice is green.

   Give each child only its role's phase: a `test-writer` task authorizes test changes but no production-code implementation; an `implementer` task authorizes production-code changes for an already-red test but no new behavior tests. Never combine test writing and production-code implementation in one child task or run. Throughout implementation, hunt the code-judo move that deletes whole branches, helpers, or layers; keep files under 1k lines; never add special-case branches or one-off flags to unrelated or shared flows; prefer direct, boring code and reuse the existing canonical helper in the owning layer. Done when every planned slice is green.
4. **Verify.** Run the project's required focused and full verification commands in an authorized session; the orchestrator runs commands denied to children and supplies results as parent evidence. Done when every command passes.
5. **Review once, in parallel.** After all slices are implemented and verified, automatically dispatch all four reviewers in one fresh-context workflow, including for tiny direct edits:
   - `code-reviewer` to review the complete tests and implementation for concrete correctness, spec, and standards defects;
   - `test-reviewer` to review the changed tests and meaningful test gaps against the `tdd` skill;
   - `thermonuclear-reviewer` to review the complete change for structural regressions and clear, material simplifications; and
   - `global-reviewer` to follow the `global-impact-review` skill, inspecting relevant unchanged paths for missed end-to-end consequences and user follow-ups. Keep its configured model and thinking level; do not downgrade it for small changes.

   Give reviewers the user goal, approved scope and decisions, repository location, exact change boundary (including relevant untracked files), resolved revisions, current index result, relevant scoped diff and verification results. Supply the diff inline or as an authorized readable artifact for headless reviewers, including `global-reviewer`; its inspection must extend beyond that diff. Follow `~/.pi/agent/GUARDRAILS.md` for evidence attribution.

   Wait for all four reviewers, then synthesize their reports. Accept code repairs only for blockers and high-confidence defects or omissions needed to deliver the approved behavior. If accepted findings exist, perform one role-separated repair pass, update tests when behavior changes, and rerun only the checks affected by the repair. Do not start another open-ended review cycle. Escalate scope expansions and unresolved product/architecture decisions to the user rather than implementing them automatically. Retain relevant operational actions, conditional cautions, and future stories separately as user follow-ups, not as rejected code findings; record each finding's disposition. Done when accepted findings are fixed, affected checks pass, and remaining follow-ups are retained for delivery. If a blocker remains, a reviewer could not complete, or reviewers disagree on a product or architecture decision, stop and ask the user.
6. **Documentation.** Follow the project's documentation instructions and verify that its documentation reflects the latest change, updating it when needed. Done when the documentation is current.
7. **Verification and handoff.** Summarize what changed and what was verified. Include retained global-review follow-ups in the user-facing conclusion: action, why/when it matters, and whether required before rollout or optional later. Distinguish completed code from pending operational work; carry unresolved follow-ups into the final response after commit as well. Ask the user to check that everything is correct. Wait for confirmation. Done when follow-ups have been delivered and the user confirms.
8. **Commit.** Commit the complete verified, reviewed, and documented change with a focused message.
9. Suggest a push and pull request creation after a vertical slice is fully implemented.

Manage your context with subagents. Each role-specific agent above already preloads its required skill; do not attach the skill again at dispatch. Use read-only agents for exploration and scoping, one writer at a time, and keep your context for orchestration, synthesis, and decisions.
